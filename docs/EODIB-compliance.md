# zabbix-mcp-server: соответствие требованиям ИБ (для задачи ЕОДИБ)

Документ описывает модель безопасности zabbix-mcp-server в контуре за шлюзом Higress.
Схема повторяет уже внедрённый netbox-mcp-server; отличия, связанные с двумя
экземплярами Zabbix, отмечены отдельно.

## 1. Архитектура и поток запроса

```
Потребитель (Kilocode/чат-клиент)
  → Higress (OAuth/Keycloak, security-заголовки)
    → zabbix-mcp-server (AUTH_MODE=per_request_token, HTTP, read-only)
      → Zabbix API: zabbix-ut   (персональный токен пользователя, часть "ut=" из X-MCP-Token)
      → Zabbix API: zabbix-uts  (персональный токен пользователя, часть "uts=" из X-MCP-Token)
```

Сервисная УЗ к Zabbix не используется. Каждый запрос несёт персональные API-токены
пользователя: по одному на каждый экземпляр Zabbix. MCP опубликован единым маршрутом,
а Higress расшифровывает один заголовок `X-MCP-Token`, поэтому оба токена передаются в
нём строкой `ut=<токен>;uts=<токен>`, зашифрованной целиком. Сервер разбирает её и
отправляет в каждый экземпляр только его токен. Сервер
подключается к Zabbix с токеном из текущего запроса и никогда не откатывается на
статический токен. Если токена нужного экземпляра в запросе нет, обращение к этому
экземпляру отклоняется.

## 2. Ролевая модель

**Авторизация делегирована целевой системе (Zabbix).** Что видит пользователь,
определяется ролью и группами его пользователя в Zabbix, которому выпущен токен.
MCP-сервер решений о правах не принимает и собственного RBAC не реализует.

Дополнительно на стороне MCP:
- все инструменты, способные изменять данные (138), заблокированы списком
  `blocked_write_tools.txt` и не публикуются; они же отклоняются по имени метода
  в универсальных вызовах;
- запись на каждом экземпляре Zabbix запрещена отдельно (`READ_ONLY=true`);
- инструменты, работающие с пользователями Zabbix (`user`, `usergroup`,
  `userdirectory`, `role`, `token`, `mfa`), исключены полностью;
- набор публикуемых инструментов ограничивается группами (`ZABBIX_MCP_SERVER__TOOLS`).

Token Passthrough в смысле спецификации MCP отсутствует: аутентификация к MCP
выполняется на Higress, а содержимое `X-MCP-Token` — credentials к downstream-системам.

## 3. Контракт заголовков

| Заголовок | Назначение | Доверие |
|-----------|-----------|---------|
| `X-Request-By` | Режим (`personal`) | Проверяется (allow-list) |
| `X-MCP-Token` | Персональные токены `ut=<токен>;uts=<токен>` (расшифрованы Higress) | Credentials к Zabbix-UT и Zabbix-UTS |
| `X-MCP-Request-Principal` | Заявленная личность | **Недоверенный**, только для журнала |
| `X-Request-Id` | Корреляция для аудита | Информационный |

Запрос без `X-Request-By` из списка или без хотя бы одного токена Zabbix получает `401`.

## 4. Матрица технических мер

| Требование ИБ | Реализация |
|---------------|-----------|
| Аутентификация запроса | Higress (OAuth/Keycloak) + обязательные `X-Request-By` и токен Zabbix; иначе `401` |
| Разграничение доступа | Штатные роли Zabbix по персональному токену |
| Read-only | Блок-лист изменяющих инструментов, `READ_ONLY=true`, рекомендуется роль Zabbix без прав записи |
| HTTPS | TLS-терминация на шлюзе; HSTS в ответах; к Zabbix только с проверкой сертификата |
| Security-заголовки | `X-Content-Type-Options`, `X-Frame-Options`, `X-XSS-Protection: 0`, `Content-Security-Policy: default-src 'none'`, `Referrer-Policy`, HSTS |
| Отсутствие сессионного захвата | `stateless_http` — токен не привязывается к сессии |
| Блокировка небезопасного PROD | При `per_request_token` старт отклоняется для `transport=stdio`, `log_level=debug`, `verify_ssl=false` |
| Ограничение поверхности | Группы инструментов, блок-лист записи, исключение пользователей Zabbix |
| Таймауты и лимиты | Таймаут запроса к Zabbix, 300 вызовов/мин на токен, ответ не более 50 000 символов |
| Аудит | Логгер `zabbix_mcp.audit`: инструмент, экземпляр, имена аргументов, заявленный principal, correlation-id, результат, длительность |
| Защита секретов | Токены не логируются; переменные `ZABBIX_*` окружения процесса игнорируются |
| Контейнер | non-root (`nobody`), read-only rootfs с `/tmp` в `emptyDir`, закреплённые версии зависимостей |

## 5. Модель угроз (кратко)

Основной вектор — компрометация рабочей станции, где в конфиге клиента лежат токены.
Компенсирующие меры на стороне Zabbix: отдельный пользователь с ролью только для
чтения, срок действия токена, минимальный набор групп хостов.

## 6. Организационные вопросы к Higress / инфраструктуре (вне кода)

- Принимает ли процедура шифрования для Higress произвольную строку
  (`ut=<токен>;uts=<токен>`), а не только сам токен. **Требует подтверждения.**
- Достижимость пода MCP только со шлюза (NetworkPolicy): `X-Request-By` — метка,
  а не аутентификация.
- TTL, ротация и отзыв токенов Zabbix; регламент их выпуска.
